## 2. របៀបរៀបចំ Project Structure

ខ្ញុំចូលចិត្តបែងចែក Responsibilities ឱ្យបានច្បាស់លាស់ ជាជាងដាក់ Routes, Database Queries និង Application Logic ទាំងអស់នៅក្នុង File តែមួយ។

ខាងក្រោមគឺជា Structure សាមញ្ញរបស់ Project៖

```text
src/
├── app.ts
├── server.ts
├── controllers/
├── docs/
├── lib/
│   └── prisma.ts
├── middleware/
└── routes/
    └── v1/

prisma/
├── schema.prisma
└── migrations/

test/
docker-compose.yml
package.json
```

Folder នីមួយៗមានតួនាទីផ្សេងៗគ្នា៖

- `app.ts` — សម្រាប់រៀបចំ Express Application និង Middleware។
- `server.ts` — សម្រាប់ចាប់ផ្តើម HTTP Server។
- `controllers/` — សម្រាប់គ្រប់គ្រង Requests និង Responses។
- `routes/v1/` — សម្រាប់កំណត់ API Endpoints តាម Version។
- `middleware/` — សម្រាប់គ្រប់គ្រង Error Handling និង Middleware ផ្សេងៗ។
- `lib/prisma.ts` — សម្រាប់គ្រប់គ្រង Prisma Client។
- `docs/` — សម្រាប់រក្សាទុក API Documentation។
- `prisma/` — សម្រាប់រក្សាទុក Database Schema និង Migrations។
- `test/` — សម្រាប់រក្សាទុក API Tests។

គោលបំណងរបស់ខ្ញុំមិនមែនចង់បង្កើត Folder ច្រើនៗដោយមិនចាំបាច់នោះទេ ប៉ុន្តែចង់ឱ្យ Project មានគ្រឹះល្អមុននឹងបន្ថែម Features ថ្មីៗ។

## 3. ការបែងចែក Routes និង Controllers

បញ្ហាមួយដែលខ្ញុំចង់ជៀសវាងគឺការសរសេរ Business Logic ច្រើនពេកនៅក្នុង Route Handler។

ខ្ញុំចូលចិត្តឱ្យ Route មានតួនាទីកំណត់ Endpoint និងបញ្ជូន Request ទៅ Controller ដែលត្រូវគ្នា។

ឧទាហរណ៍៖

```ts
import { Router } from "express";
import {
  getUsers,
  createUser,
} from "../controllers/user.controller";

const router = Router();

router.get("/users", getUsers);
router.post("/users", createUser);

export default router;
```

ចំណែក Controller មានតួនាទីគ្រប់គ្រង HTTP Request និង Response។

នៅពេល Business Logic កាន់តែស្មុគស្មាញ យើងអាចបំបែកវាទៅក្នុង Service Layer ដាច់ដោយឡែក។

វិធីនេះជួយឱ្យ Code ងាយស្រួលអាន ងាយស្រួលធ្វើ Testing និងងាយស្រួលថែទាំ។

ឧទាហរណ៍ Users ខាងលើគឺជាគំរូសម្រាប់បង្ហាញពីរបៀបរៀបចំ Feature នាពេលអនាគត មិនមែនជា Feature ដែលបានបញ្ចប់រួចនៅក្នុង Repository នោះទេ។

## 5. Centralized Error Handling

ការគ្រប់គ្រង Error គឺជាផ្នែកសំខាន់មួយក្នុងការអភិវឌ្ឍ Backend Application។

ជំនួសឱ្យការសរសេរ Error Response ដដែលៗនៅគ្រប់ Controller ខ្ញុំចូលចិត្តប្រើ Middleware មួយសម្រាប់គ្រប់គ្រង Error។

ឧទាហរណ៍៖

```ts
import type {
  ErrorRequestHandler,
} from "express";

export const errorHandler: ErrorRequestHandler = (
  err,
  req,
  res,
  next
) => {
  console.error(err);

  res.status(500).json({
    success: false,
    message: "Internal server error",
  });
};
```

នេះគ្រាន់តែជា Basic Example ប៉ុណ្ណោះ។

សម្រាប់ Production Application យើងគួរគ្រប់គ្រង Error Types ផ្សេងៗ ដូចជា Validation Errors, Authentication Errors និង Internal Server Errors ដោយប្រើ HTTP Status Codes ឱ្យបានត្រឹមត្រូវ។

ការប្រើ Centralized Error Handling ជួយឱ្យ Error Responses មានទម្រង់ស្របគ្នា និងកាត់បន្ថយ Code ដែលសរសេរដដែលៗ។

## 6. PostgreSQL និង Prisma ORM

សម្រាប់ Database ខ្ញុំប្រើ PostgreSQL ជាមួយ Prisma ORM។

Prisma ជួយឱ្យយើងងាយស្រួលក្នុងការកំណត់ Models គ្រប់គ្រង Database Migrations និងសរសេរ Queries ដែលមាន Type Safety។

ឧទាហរណ៍ User Model ដែលអាចបន្ថែមនៅពេលក្រោយ៖

```prisma
model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?
  createdAt DateTime @default(now())
}
```

ខ្ញុំក៏ចូលចិត្តរៀបចំ Prisma Client នៅក្នុង Shared Module មួយ ជាជាងបង្កើត Client ថ្មីនៅគ្រប់ Controller។

វិធីនេះជួយឱ្យការគ្រប់គ្រង Database Connection មានភាពងាយស្រួល។

បច្ចុប្បន្ន Project នេះផ្តោតទៅលើការរៀបចំគ្រឹះ Backend ជាមុនសិន។ Business Models អាចត្រូវបានបន្ថែមនៅពេលមាន Requirements ច្បាស់លាស់។

## 9. API Testing

ខ្ញុំក៏ចូលចិត្តរៀបចំ API Testing ជាផ្នែកមួយនៃ Project Foundation ផងដែរ។

Testing ជួយផ្ទៀងផ្ទាត់ថា Endpoints ដំណើរការតាមអ្វីដែលយើងរំពឹងទុក និងជួយកាត់បន្ថយបញ្ហានៅពេលកែប្រែ Code។

ឧទាហរណ៍ Health Check Test ដោយប្រើ Supertest៖

```ts
import request from "supertest";
import app from "../src/app";

describe("Health Check", () => {
  it("should return HTTP 200", async () => {
    const response = await request(app)
      .get("/health");

    expect(response.status).toBe(200);
  });
});
```

នេះគ្រាន់តែជាឧទាហរណ៍សម្រាប់បង្ហាញគំនិតនៃ Testing ប៉ុណ្ណោះ។ Endpoint និង Test Configuration ត្រូវកំណត់ឱ្យស្របតាម Project ពិតប្រាកដ។

នៅពេលបន្ថែម Features ថ្មីៗ ខ្ញុំគ្រោងនឹងផ្តោតលើ Request Validation, Authentication, Business Logic និង Error Handling Tests ផងដែរ។

## 10. ហេតុអ្វីខ្ញុំចាប់ផ្តើមពី Architecture សាមញ្ញ?

មិនមែនគ្រប់ Application ទាំងអស់សុទ្ធតែត្រូវការប្រើ Microservices តាំងពីដំបូងនោះទេ។

សម្រាប់ Project ថ្មី ខ្ញុំចូលចិត្តចាប់ផ្តើមពី **Monolith ដែលមាន Structure ល្អ**។

វាងាយស្រួលក្នុងការអភិវឌ្ឍ Debug Deploy និងថែទាំ នៅពេល Application នៅមានទំហំតូច។

នៅពេល System កាន់តែធំ យើងអាចពិនិត្យមើល Requirements ជាក់ស្តែង ហើយសម្រេចថាតើត្រូវកែប្រែ Architecture ឬអត់។

សម្រាប់ខ្ញុំ Software Architecture ល្អមិនមែនមានន័យថាត្រូវប្រើ Technologies ឬ Design Patterns ច្រើននោះទេ។

អ្វីដែលសំខាន់គឺជ្រើសរើសវិធីសាស្ត្រដែលសមស្របនឹង Project និងធ្វើឱ្យ Codebase ងាយស្រួលគ្រប់គ្រង។
